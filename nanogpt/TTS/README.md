# TTS autoresearch search runner

`TTS/run_a_search_nanogpt.py` runs test-time search over `train.py`. Each node in the
search tree is a complete candidate `train.py`; each action is an LLM-generated code
edit applied to its parent. Candidates are evaluated by executing the generated file and
parsing a score such as `val_bpb` from `train.py` diagnostics or stdout.

## Quick commands

Run best-of-N with two one-step rollout branches from the current `train.py`:

```bash
python3 TTS/run_a_search_nanogpt.py \
  --method best_of_n \
  --breadth 2 \
  --depth 1
```

For `best_of_n`, `--breadth` is the number of independent branches and `--depth` is
the number of sequential state transitions per branch. For example, `--breadth 2
--depth 4` evaluates eight candidates arranged as two independent depth-4 paths from
the seed state.

Run beam search with breadth 3, depth 2, keeping the top 2 states per level:

```bash
python3 TTS/run_a_search_nanogpt.py \
  --method beam_search \
  --breadth 3 \
  --depth 2 \
  --beam-width 2 \
  --max-evaluations 6
```

Run MCTS with UCT selection. Here `--breadth` is the maximum children per node,
`--depth` is the rollout depth limit, and `--beam-width` is used as the exploration
constant:

```bash
python3 TTS/run_a_search_nanogpt.py \
  --method mcts \
  --breadth 3 \
  --depth 3 \
  --beam-width 2 \
  --max-evaluations 9
```

Run against the fast mock objective in `TTS/mock_train.py`:

```bash
python3 TTS/run_a_search_nanogpt.py \
  --train-file TTS/mock_train.py \
  --method mcts \
  --breadth 2 \
  --depth 2 \
  --max-evaluations 4 \
  --eval-command "python3 {train_path}"
```

Search progress is shown on stderr as a compact bar with the current best score. Use
`--no-progress` to disable it or `--progress-width 40` to make it wider.

Run dynamically expanded operation-feature model-based search:

```bash
python3 TTS/run_expanded_search.py \
  --generator operation_tool \
  --operation-schema TTS/operation_schema_real_train.json \
  --train-file TTS/real_train.py \
  --initial-operation-features 5 \
  --method best_of_n \
  --breadth 4 \
  --depth 2 \
  --iterations 10 \
  --warmup 5 \
  --eval-command "uv run python {train_path}"
```

`run_expanded_search.py` starts the GP on an active subset of schema parameters.
During generation the model can either call `propose_train_operations` to edit active
features or `propose_operation_feature` to activate one inactive schema parameter as a
new GP dimension. The run writes `operation_schema.json` for the full feature pool,
`active_operation_schema.json` for the current GP feature space, and
`operation_feature_expansions.json` for the activation history.

Allow multiple LLM edit passes inside each single state transition:

```bash
python3 TTS/run_a_search_nanogpt.py \
  --train-file TTS/mock_train.py \
  --method best_of_n \
  --breadth 2 \
  --depth 1 \
  --num-edits-per-step 3 \
  --generator mock \
  --eval-command "python3 {train_path}"
```

With `--num-edits-per-step 3`, each child state is generated by applying three
sequential patches before evaluation. The second and third prompts include the patches
already applied within that transition. Each state directory stores `prompt_edit_01.md`,
`response_edit_01.md`, `patch_edit_01.diff`, etc., and the state JSON includes an
`edits` array.

Control how often generated search depths are evaluated with `--eval-each-num-steps`.
The default `1` evaluates every generated depth. A value of `2` expands two code-edit
steps before running the training/evaluation command:

```bash
python3 TTS/run_a_search_nanogpt.py \
  --train-file TTS/mock_train.py \
  --method best_of_n \
  --breadth 2 \
  --depth 2 \
  --eval-each-num-steps 2 \
  --generator mock \
  --eval-command "python3 {train_path}"
```

States generated between evaluation boundaries are logged with
`status="evaluation_deferred"` and no score. The final depth is always evaluated, even
when it is not an exact multiple of the interval, so a completed run still produces
scored candidates.

Every coder-LLM prompt includes built-in benchmark context: `train.py` is the only
editable file, it contains the full model/optimizer/training loop, training is scored
under a fixed 300 second budget, and `val_bpb` is the primary lower-is-better metric.
Append additional task context from a README or notes file with `--context-file`:

```bash
python3 TTS/run_a_search_nanogpt.py \
  --train-file TTS/real_train.py \
  --method best_of_n \
  --breadth 1 \
  --depth 1 \
  --context-file TTS/README.md \
  --eval-command "uv run python {train_path}"
```

Use `--context "..."` for short inline context and `--instruction "..."` for more
specific per-run steering. The context is shown before the objective and edit-format
instructions in each saved `prompt.md`.

The preferred LLM edit response is a SEARCH/REPLACE block:

```text
train.py
<<<<<<< SEARCH
exact code from the current train.py
=======
replacement code
>>>>>>> REPLACE
```

The runner applies these blocks before trying fallback unified diffs or complete-file
responses. SEARCH text must match exactly and uniquely; this tends to be easier for code
LLMs than producing perfect line-numbered patches. Keep edits neat and minimal: for a
one-line hyperparameter change, use that one exact line as SEARCH and replacement. Do
not wrap a small change in a large unchanged setup/model/optimizer/dataloader/training
section, because a stray blank line in that large span can make the edit fail.

Test the plumbing without calling an LLM or launching training:

```bash
python3 TTS/run_a_search_nanogpt.py \
  --method tree_search \
  --breadth 2 \
  --depth 2 \
  --generator mock \
  --skip-eval \
  --out-dir /tmp/tts_mock_run
```

`--out-dir` is a parent directory for runs. Each invocation creates a tagged child
folder inside it, for example
`/tmp/tts_mock_run/tree_search_mock_train_b2_d2_e1_20260623_153045/`. Use
`--run-name my_test` to choose the child folder name; if it already exists, the runner
adds a numeric suffix.

Use an SGLang Qwen3-Coder server with tool-call parsing:

```bash
sglang serve \
  --model-path /mnt/data0/hf_models/models/Qwen3-Coder-30B-A3B-Instruct \
  --served-model-name Qwen3-Coder-30B-A3B-Instruct \
  --trust-remote-code \
  --tp 2 \
  --ep 2 \
  --tool-call-parser qwen3_coder \
  --host 0.0.0.0 \
  --port 52307

TTS_LLM_URL=http://127.0.0.1:52307/v1 \
TTS_LLM_MODEL=Qwen3-Coder-30B-A3B-Instruct \
python3 TTS/run_a_search_nanogpt.py \
  --generator tool_call \
  --train-file TTS/mock_train.py \
  --method best_of_n \
  --breadth 1 \
  --depth 1 \
  --eval-command "python3 {train_path}"
```

In `tool_call` mode the runner sends an OpenAI-compatible `tools` schema named
`edit_train_py`. If SGLang parses the model output into `message.tool_calls`, TTS
serializes that call into `response.md`, extracts the JSON arguments, and applies the
`edits` array directly as exact search/replace edits. SEARCH/REPLACE text and unified
diff responses remain fallbacks for servers without tool-call parsing.

Request output-token logprobs from SGLang/OpenAI-compatible endpoints with
`--logprobs`; add `--top-logprobs N` to include top alternatives per generated token:

```bash
TTS_LLM_URL=http://127.0.0.1:52307/v1 \
TTS_LLM_MODEL=Qwen3-Coder-30B-A3B-Instruct \
python3 TTS/run_a_search_nanogpt.py \
  --generator tool_call \
  --train-file TTS/real_train.py \
  --method best_of_n \
  --breadth 1 \
  --depth 1 \
  --logprobs \
  --top-logprobs 5 \
  --eval-command "uv run python {train_path}"
```

Each edit stores a compact `logprob_summary` in `meta.json`. The progress display also
shows a short form such as `lp=-0.24 ppl=1.27 lptok=512` when logprobs are available.
The full provider payload is saved as `logprobs.json` or `logprobs_edit_01.json` for
multi-edit transitions.

Tool-call edits are applied sequentially. The model is instructed to avoid overlapping
edits; if it still emits a redundant nested edit, the runner treats a later edit as
already satisfied only when that later replacement text is already present exactly once.
Detected edit attempts are recorded in `meta.json` even if application fails. Exact
SEARCH matches are preferred, but the applier has a narrow fallback for unique matches
that differ only in blank-line counts or trailing spaces.

Use the Hermes-style harness generator for a short inspect/edit/finish tool loop before
the search state is finalized:

```bash
TTS_LLM_URL=http://127.0.0.1:52307/v1 \
TTS_LLM_MODEL=Qwen3-Coder-30B-A3B-Instruct \
python3 TTS/run_a_search_nanogpt.py \
  --generator harness \
  --train-file TTS/real_train.py \
  --method best_of_n \
  --breadth 1 \
  --depth 1 \
  --eval-command "uv run python {train_path}"
```

The harness mode follows the same pattern as code-agent harnesses such as
NousResearch Hermes Agent: the model can call tools to inspect the current `train.py`,
apply neat exact replacements, observe success or failure, and then finish. The final
applied edits are serialized back into SEARCH/REPLACE blocks, so the normal TTS logging,
patch creation, and evaluation path still apply.

To test only the tool-call edit function on `TTS/real_train.py` without running search:

```bash
TTS_LLM_URL=http://127.0.0.1:52307/v1 \
TTS_LLM_MODEL=Qwen3-Coder-30B-A3B-Instruct \
python3 TTS/test_tool_call_edit.py
```

This writes `response_*.md`, `patch_*.diff`, and an edited copy under
`TTS/tool_call_tests/`. Add `--apply` only if you want to overwrite `TTS/real_train.py`.

## Model-Based Search

`TTS/run_model_based_search.py` wraps the normal code-edit search in an outer
surrogate-model loop. Each outer iteration:

1. builds a tree of LLM-edited candidate `train.py` files,
2. scores generated nodes with a Gaussian-process surrogate trained from previous real
   evaluations,
3. selects one promising candidate, usually from the leaves,
4. executes only that selected candidate, and
5. appends the real score and code features to a reusable JSONL buffer.

This is useful when real training runs are expensive: the tree search can still explore
many code edits, but only the final selected candidate in each iteration consumes a real
evaluation. The next iteration refits the GP from the expanded buffer.

Fast mock smoke test:

```bash
python3 TTS/run_model_based_search.py \
  --train-file TTS/mock_train.py \
  --generator mock \
  --method best_of_n \
  --breadth 2 \
  --depth 2 \
  --iterations 2 \
  --eval-command "python3 {train_path}" \
  --no-progress
```

Example real run:

```bash
python3 TTS/run_model_based_search.py \
  --train-file TTS/real_train.py \
  --generator tool_call \
  --method best_of_n \
  --breadth 2 \
  --depth 4 \
  --iterations 8 \
  --buffer TTS/model_based_buffer.jsonl \
  --eval-command "uv run {train_path}"
```

Fixed-dimension operation search constrains the LLM to a schema of named knobs instead
of arbitrary code patches. In `operation_tool` mode the model must call
`propose_train_operations`; the runner validates every operation, rejects unknown
dimensions or out-of-range values, and deterministically rewrites only matching
top-level assignments in `train.py`. The same schema also defines the GP feature vector,
so the surrogate learns over a stable operation space:

```bash
python3 TTS/run_model_based_search.py \
  --train-file TTS/real_train.py \
  --generator operation_tool \
  --operation-schema TTS/operation_schema_real_train.json \
  --method best_of_n \
  --breadth 2 \
  --depth 4 \
  --iterations 8 \
  --max-operations-per-step 2 \
  --buffer TTS/model_based_buffer.jsonl \
  --eval-command "uv run {train_path}"
```

For local plumbing tests without an LLM, use `operation_mock` with
`TTS/operation_schema_mock_train.json`:

```bash
python3 TTS/run_model_based_search.py \
  --train-file TTS/mock_train.py \
  --generator operation_mock \
  --operation-schema TTS/operation_schema_mock_train.json \
  --method best_of_n \
  --breadth 2 \
  --depth 2 \
  --iterations 2 \
  --eval-command "python3 {train_path}"
```

Operation-mode runs copy the schema to `operation_schema.json` in the run directory.
Each operation state saves `operations.json`, `patch.diff`, and the final `train.py`.
Buffer rows use feature versions such as `operation_schema:real_train_knobs_v1`; old
buffer rows with a different feature version or dimension are skipped instead of mixed
into the GP fit.

Use warm-up rounds when the GP starts with too little data. Warm-up candidates are real
evaluated before iteration 1 and appended to the same buffer. With fixed-operation
search, `--warmup-strategy auto` samples valid random schema operations by default, so
the GP can see diverse feature/score pairs before it guides BoN/tree/beam search:

```bash
python3 TTS/run_model_based_search.py \
  --train-file TTS/real_train.py \
  --generator operation_tool \
  --operation-schema TTS/operation_schema_real_train.json \
  --method best_of_n \
  --breadth 2 \
  --depth 4 \
  --iterations 8 \
  --warmup 6 \
  --warmup-include-root \
  --max-operations-per-step 2 \
  --buffer TTS/model_based_buffer.jsonl \
  --eval-command "uv run {train_path}"
```

Warm-up points use `iteration=0` in `model_based_buffer.jsonl`, and
`model_based_summary.json` includes a `warmup` section with state ids, scores, RNG seed,
and GP fit status after warm-up. By default warm-up trains only the GP buffer and does
not change the first search root selected by `--seed-policy`; pass
`--warmup-updates-seed` if warm-up candidates should also count as latest/best seed
candidates before iteration 1.

The runner also writes an iteration feedback memory at `iteration_feedback.tsv` and
injects a compact version into later LLM prompts. Each real evaluated trial records the
state id, action summary or operation path, execution status, parsed score, surrogate
prediction fields, and whether it improved the previous best. Use `--feedback-max-rows`
to control how many feedback rows are shown to the LLM, or `--feedback-tsv` to choose a
custom TSV path.

Plot the final learned GP surrogate from a completed model-based run:

```bash
python3 TTS/plot_gp_model.py \
  TTS/runs/model_based/my_run \
  --slice-params DEPTH,WIDTH,MATRIX_LR,WARMDOWN_RATIO
```

This writes `gp_plots/observed_vs_predicted.png`, `gp_plots/feature_pca.png`,
one `gp_plots/slice_<PARAM>.png` per requested schema parameter, and
`gp_plots/summary.json`. Because the GP is learned over the full feature vector, the
slice plots show 1D cross-sections through the best observed point rather than the
entire high-dimensional surface.

Important knobs:

- `--method best_of_n|tree_search|beam_search` chooses the inner surrogate-guided
  search shape. `auto` is the default and uses `tree_search` when `--beam-width 0`, or
  `beam_search` when `--beam-width` is positive.
- For `best_of_n`, `--breadth` is the number of independent branches and `--depth` is
  the number of sequential code-edit steps per branch. For example, `--breadth 2
  --depth 4` generates two depth-4 paths and then evaluates the best selected leaf.
- For `tree_search`, `--breadth` and `--depth` generate the full tree for each outer
  iteration.
- For `beam_search`, `--breadth` controls children per beam parent and `--beam-width`
  controls how many surrogate-ranked states survive to the next depth.
- `--select-from leaves|all` controls whether the real evaluation is chosen only from
  final leaves or from every surrogate-scored state.
- `--seed-policy original|latest|best` controls whether the next iteration starts from
  the original seed, the most recently evaluated candidate, or the best evaluated
  candidate.
- `--surrogate-mode lcb|mean|ei` controls the acquisition score. `lcb` is the default
  lower-confidence-bound mode for lower-is-better metrics.
- `--evaluate-root` can add the initial seed state to the buffer before the first model
  based selection.
- `--warmup N` evaluates N warm-up candidates before model-based iterations. For
  operation generators, `--warmup-strategy auto` samples random valid schema operations;
  for free-form generators it asks the configured agent to propose warm-up edits.
- `--skip-eval` generates and surrogate-scores candidates without appending new real
  data to the buffer.
- Progress is shown on stderr as a single model-based progress bar. It advances for
  each generated surrogate-scored state and each real evaluation; use `--no-progress` to
  keep the run quiet. The bar and `model_based.log` also show GP fit status. Because
  this is an exact GP fit rather than iterative neural training, the loss-like value is
  `nlml`, the negative log marginal likelihood on normalized targets. Each iteration
  records the selected real `val_bpb`, the previous best, the new best, and whether the
  iteration improved the previous best in `model_based_summary.json`.

By default the live buffer is saved inside the run directory as
`model_based_buffer.jsonl`, so each run is self-contained. Pass `--buffer` when you want
to reuse a buffer across multiple runs; `--buffer` may point directly to a JSONL file,
a previous model-based run directory, or a previous `model_based_summary.json`. The
runner refits the GP from that buffer at startup and after each new real evaluation;
there is no separate serialized GP object to manage. It updates that external buffer
and also keeps a run-local `model_based_buffer.jsonl` snapshot. A run writes the normal
`summary.json`, `model_based_summary.json`, and a concise orchestration log at
`model_based.log`; each state still stores its own prompt, response, patch, evaluation
logs, and surrogate fields in `meta.json`.

Failed or sentinel-score evaluations are excluded from GP training by default. Rows with
failed statuses such as `crash`, `timeout`, `score_missing`, or `evaluation_error`, and
lower-is-better scores at or above `--failure-score` such as `1e+09`, are not loaded
from old buffers and are not appended after new evaluations. Override the numeric
threshold with `--gp-reject-score-at-or-above` or `--gp-reject-score-at-or-below`; pass
`--gp-allow-failure-status` only if you intentionally want failed runs in the surrogate
training data.

## Outputs

The runner writes one tagged directory per search under `TTS/runs/` by default, or under
the parent path passed to `--out-dir`. For example, `--out-dir TTS/runs/bon` creates
something like
`TTS/runs/bon/best_of_n_tool_call_real_train_b1_d1_e1_20260623_153045/`.
Each state directory contains:

- `train.py`: the candidate script.
- `prompt.md`: prompt sent to the code LLM.
- `response.md`: raw LLM response.
- `patch.diff`: normalized edit applied to the parent.
- `stdout.log` / `stderr.log`: evaluation logs.
- `diagnostics.json`: candidate diagnostics when `train.py` writes them.
- `meta.json`: state metadata, parsed score, paths, and the inline raw LLM response.

The run root contains:

- `manifest.jsonl`: append-only state event log.
- `summary.json`: full final search summary.
- `best_train.py`: the best candidate when at least one state is scored.

Render the saved search tree in the terminal:

```bash
python3 TTS/visualize_search.py TTS/runs --latest
```

This prints each state as a parent-child tree with the state id/status, action summary,
and evaluated score when available. At the end of each run, it also prints the optimal
path from the root state to the best evaluated state as an ordered action list. It reads
`summary.json` for completed runs and falls back to the latest record for each state in
`manifest.jsonl`, so it can also inspect in-progress runs:

When states contain saved `logprob_summary` records, the visualizer also shows a compact
`lp=... ppl=... lptok=...` column. Use `--no-logprobs` to hide it.

For model-based runs, the visualizer also shows surrogate columns when available:
`sg` is the lower-is-better selection score, `pred` is the GP mean prediction, `std` is
the predictive standard deviation, and `ei` is expected improvement. Use
`--no-surrogate` to hide these columns.

```bash
python3 TTS/visualize_search.py TTS/runs/mcts_20260622_185946 --show-errors
python3 TTS/visualize_search.py TTS/runs --run mcts --watch 2
```

For model-based runs with multiple outer iterations, the default view renders the whole
run as a forest with one root per iteration. Use `--iteration N` to inspect one outer
iteration at a time:

```bash
python3 TTS/visualize_search.py TTS/runs/bon/my_model_based_run --iteration 1
python3 TTS/visualize_search.py TTS/runs/bon/my_model_based_run --iteration 2
```

For a prettier topology-first tree, install PrettyPrintTree and pass `--pretty`:

```bash
pip install PrettyPrintTree
python3 TTS/visualize_search.py TTS/runs/bon/my_run --pretty
python3 TTS/visualize_search.py TTS/runs/bon/my_run --pretty --pretty-action-width 42
python3 TTS/visualize_search.py TTS/runs/bon/my_run --pretty --pretty-border
```

The visualizer includes a small compatibility shim for PrettyPrintTree environments
that fail while importing `cmd2.ansi`.

`meta.json`, `manifest.jsonl`, and `summary.json` include `llm_response`,
`llm_response_truncated`, `response_path`, `prompt_path`, and `patch_path` for each state.
The complete response is always stored in `response.md`. Use `--response-log-chars -1`
to inline full responses into JSON logs, or `--response-log-chars 0` to store only paths.

Evaluation commands should include `{train_path}` so the runner executes the generated
candidate state, for example `--eval-command "uv run python {train_path}"`. If the
placeholder is missing, the runner prints a warning because it would evaluate the same
fixed file each time.

Some OpenAI-compatible providers can return `message.content = null` when they emit only
hidden reasoning, tool calls, or filtered content. The runner normalizes this to an empty
response, saves the raw response artifact, and marks the state as a generation error with
a clear message instead of crashing while writing `response.md`.

By default the objective is `val_bpb` and lower is better. Use `--score-key` and
`--maximize` for other metrics.
